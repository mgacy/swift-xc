# swift-xc

A single SwiftPM package (Swift 6.2, macOS 15+) producing the `xc` CLI and the
`XCCore` library. Early development — there are no released consumers, so
backwards compatibility is not a concern. Break things when it makes the design
cleaner rather than adding compatibility shims.

## Agent configuration is generated — edit `.rulesync/`

`CLAUDE.md`, `AGENTS.md`, `.claude/`, and `.codex/` are **generated output**.
Editing them directly loses the change on the next generate. The sources of
truth are:

| To change | Edit | Then run |
|---|---|---|
| These instructions | `.rulesync/rules/*.md` | `mise run rulesync` |
| Hooks | `.rulesync/hooks.jsonc` + `.rulesync/hooks/*.sh` | same |
| Permissions | `.rulesync/permissions.jsonc` | same |
| Subagents / skills / MCP | `.rulesync/{subagents,skills,mcp.jsonc}` | same |

`rulesync doctor` is read-only and diagnoses the configuration.

Vendored upstream documentation for dependencies lives in
`docs/dependencies/`, pinned to the versions this project runs — consult it
instead of guessing at a dependency's file formats or CLI.

## Commands

```bash
swift build                       # debug build
swift test                        # run all tests
swift test --filter XCCoreTests   # filter by suite or test name
swift run xc --help               # exercise the CLI from source
```

Tooling is pinned in `.mise.toml`:

```bash
mise run lint                     # swiftlint
mise run lint-fix                 # swiftlint --fix
mise run lint-ci                  # actionlint + shellcheck (workflows and shell scripts)
mise run build                    # swift build -c release
mise run prepare-release patch    # open a version-bump release PR from local main
```

`Sources/xc/Version.swift` is generated by `swift-version-file-plugin` at
release time — never hand-edit it. `mise run prepare-release <patch|minor|major>`
creates the version-bump PR; after it merges, `.github/workflows/release.yml`
publishes an `xc-macos-arm64` asset plus `SHA256SUMS`.

Editing `.mise.toml` or `.mise.local.toml` requires approval, because the
session-start hook trusts a worktree's mise config when it matches the main
checkout — an edit there becomes code that later runs.

## Code search

`sextant` (pinned in `.mise.toml`) is a structural Swift search tool. Use
`--pretty` for readable output.

```bash
mise x -- sextant lookup XCCore --pretty                  # definition site, conformances, extensions
mise x -- sextant lookup run --kind function --pretty
mise x -- sextant enum-cases Sources --enum-name Error --pretty   # cases with associated values
mise x -- sextant overview Sources/XCCore/XCCore.swift --pretty   # structure of a file or directory
mise x -- sextant references XCCore --path Sources --pretty       # declaration-level references
mise x -- sextant references Codable --path Sources --position inheritance --pretty
```

**Prefer sextant over Grep for:** where a type is defined; the cases of an enum
(regex is brittle against associated values); the structure of a file; where a
type is referenced in declarations; what conforms to a protocol.

**Use Grep instead for:** anything inside function bodies, comments, or string
literals, and for non-Swift files.

## Swift conventions

Swift 6.2 with strict concurrency. Mark `Sendable` explicitly on types that
cross concurrency boundaries.

### File header

```swift
//
//  FileName.swift
//  TargetName
//
//  Created by Mathew Gacy on M/D/YY.
//  Copyright © YYYY Mathew Gacy. All rights reserved.
//
```

### Naming

- `TypeName.swift` for a primary type
- `TypeName+Extension.swift` / `TypeName+Utils.swift` for extensions
- `TypeName+Protocol.swift` for protocol conformances
- Imports sorted alphabetically

### Access control

Be explicit. `XCCore` is a library target, so every member intended for the
`xc` executable is `public`; use `private` for implementation details,
`fileprivate` rarely, and `package` for cross-target internals.

### Organization

- Group protocol conformances into extensions, one per conformance:
  ```swift
  // MARK: - CustomStringConvertible
  extension Priority: CustomStringConvertible { }
  ```
- Divide types with `// MARK: -` sections
- Use an empty `enum` as a namespace for related constants

### Errors

Use typed throws — one error type per boundary:

```swift
func load(_ url: URL) throws(FileError) -> Data
```

### SwiftLint

Run `mise run lint` before handing work back.

## Testing

Use Apple's **Testing** framework, not XCTest:

```swift
@testable import XCCore
import Testing
```

Describe behavior in the `@Test` decorator rather than the function name:

```swift
@Test("Parser rejects a manifest with no targets")
func rejectsEmptyTargets() throws { }
```

Use `arguments:` for parameterized cases instead of duplicating a test:

```swift
@Test("Recognizes every supported extension", arguments: ["swift", "h", "m"])
func recognizesExtension(_ ext: String) throws { }
```

`Tests/XCCoreTests/` mirrors the structure of `Sources/XCCore/`. When a `@Suite`
trips SwiftLint's `type_body_length`, split it into same-file extensions grouped
by `// MARK:` — SwiftLint counts each extension separately. Promote a group to
`TypeName+Group.swift` once the file approaches `file_length`.

## Documentation

Follow Apple's conventions — doc comments feed Xcode Quick Help and DocC, so
their structure is a contract rather than a style preference.

```swift
/// Returns the clamped value.
///
/// - Parameters:
///   - value: The value to clamp.
///   - minValue: The minimum value.
///   - maxValue: The maximum value.
/// - Returns: The clamped value.
/// - Throws: `XCError.invalidRange` if `maxValue` precedes `minValue`.
```

Document return values and throwing behavior on every declaration that has
them, and include a usage example for a non-obvious API.

### What not to write

- **Document the local contract, not specific callers.** A doc says what the
  declaration *is* — inputs, outputs, throws, invariants. Naming a caller rots
  the moment that code moves.
- **Rot test.** Before keeping a sentence, ask whether it would still be true if
  every caller in this codebase were replaced. If not, delete it.
- **Write for the caller, not future-you.** Cut rationale for the road not
  taken, "not yet" snapshots of other code, `- Note:` TODOs, and editorializing
  ("crucially", "defensive").
- **Don't write the diff.** State what the declaration is, not how it differs
  from what it replaced ("now returns nil", "no longer throws"). Test: would you
  write this sentence if the code had always looked this way?
